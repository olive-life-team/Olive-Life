
## 🚨 검색 API 부하 테스트 설계 근거 및 인사이트

---

### 1. 테스트 설계 근거

#### ① 테스트 도구 선정 이유
* **k6**: Java 기반 도구(JMeter 등) 대비 리소스 소모가 적어 단일 장비에서 고부하를 안정적으로 생성합니다. JavaScript 기반 스크립팅으로 시나리오의 버전 관리가 용이합니다.
* **Docker**: Redis, MySQL, Application을 컨테이너화하여 인프라 구성의 멱등성을 보장했습니다. 이를 통해 로컬과 배포 환경 간의 성능 편차를 최소화했습니다.
* **InfluxDB & Grafana**: k6의 데이터를 실시간 시각화하여, 테스트 중 발생하는 지연 시간 및 처리량의 추이(Trend)를 모니터링 가능하게 했습니다.

#### ② 150 VUs(가상 유저) 설정 근거
* **임계점 탐색**: 사전 테스트 결과 100 VUs를 기점으로 응답 시간이 비선형적으로 급증하는 현상을 확인했습니다.
* **의도적 장애 재현**: 예상 피크 타임 접속자와 서버 사양을 고려하여, 서버 한계를 살짝 상회하는 150 VUs를 설정함으로써 시스템 마비 현상을 재현하고 분석의 대상으로 삼았습니다.

---

### 2. 문제 분석: v1 (No Cache) 시스템 붕괴

모든 요청이 DB(`MySQL`)를 직접 조회하는 v1 환경에서는 150 VUs 부하 시 시스템이 사실상 마비되었습니다.

* **지연 시간 급증**: `p(95)` 지표가 11.68초까지 치솟으며 목표치(500ms)를 23배 초과했습니다.
* **장애 현상 (Status: 0)**: 서버의 TCP Accept Queue가 포화되어 새로운 연결을 수락하지 못하고 클라이언트 사이드 타임아웃이 발생했습니다.
* **원인**: 모든 스레드가 느린 DB I/O를 기다리며 차단(Blocking)되어 HikariCP(커넥션 풀)가 고갈된 것이 결정적이었습니다.

### 3. 해결 방안: 전략별 비교 (v1, v2, v3)

| 비교 항목 | v1. No Cache (DB) | v2. Local Cache (Caffeine) | v3. Global Cache (Redis) |
| :--- | :--- | :--- | :--- |
| **저장 위치** | Disk (SSD) | **App 서버 메모리 (Heap)** | **별도 캐시 서버 (RAM)** |
| **접근 속도** | 낮음 (Disk I/O) | **매우 높음 (In-memory)** | 높음 (Network I/O 발생) |
| **데이터 정합성** | 높음 (Single Source) | **낮음 (서버간 데이터 상이)** | **높음 (공통 저장소 사용)** |
| **확장성** | 낮음 (DB 부하 집중) | 낮음 (Scale-out 시 불리) | **매우 높음 (분산 환경 최적)** |

### 5. 기술적 수확 및 인사이트

* **부하 테스트의 목적성 재정의**: 막연한 성능 개선이 아닌, 데이터 기반의 확신을 얻는 과정이었습니다. 어느 지점에서 시스템이 무너지는지(Breaking Point)를 수치로 특정함으로써, 예상 트래픽에 대응할 수 있는 가용 범위를 확정했습니다.
* **시스템 가용성에 대한 통찰**: 코드 최적화만큼이나 중요한 것이 인프라 통로(Connection Pool, Queue)의 관리임을 깨달았습니다. Status: 0 에러 분석을 통해 WAS와 DB 사이의 조율이 성능의 핵심임을 학습했습니다.
* **설계적 트레이드오프(Trade-off) 경험**: 단순히 가장 빠른 수치만 쫓았다면 v2(Local)를 선택했겠지만, 서비스의 지속 가능한 성장(Scale-out)과 데이터 정합성을 고려하여 v3를 선택했습니다. 이는 기술 선택 시 비즈니스 요구사항과 운영 안정성을 균형 있게 고려하는 계기가 되었습니다.
* **성능 개선의 원천(Disk vs Memory)**: 물리적 Disk I/O와 메모리 접근의 속도 차이를 데이터로 증명했습니다. 무거운 쿼리 연산을 단순 데이터 반환으로 전환함으로써 전체 시스템의 CPU 부하를 획기적으로 낮췄습니다.
