
# 🚨 Troubleshooting: 검색 API 성능 장애 개선 및 캐싱 전략 도입

상품 검색 API 부하 테스트 중 발생한 **시스템 마비 현상(Request Timeout)**을 분석하고, **단계별 캐싱 전략(Local & Redis)**을 적용하여 성능을 개선하고 시스템 가용성을 100% 확보한 과정

---

## 1. 🔎 배경 및 테스트 설계
* **목적**: 상품 검색 API의 병목 지점을 파악하고, 분산 환경(Scale-out)에 적합한 최적의 캐시 아키텍처 결정
* **테스트 도구**: K6, Docker, InfluxDB, Grafana
* **부하 모델**: 150 VUs까지 점진적 부하 증가(Ramp-up)

### 테스트 시나리오 (Step-by-Step)
1.  **v1 (No Cache)**: 모든 요청이 DB(`MySQL`)를 직접 조회
2.  **v2 (Local Cache)**: 애플리케이션 메모리(`Caffeine`) 내 데이터 보관
3.  **v3 (Global Cache)**: 외부 저장소(`Redis`)를 활용한 전역 캐시

---

## 2. ⚠️ 문제 상황: v1 시스템 붕괴 (Breaking Point)

150명의 가상 유저(VU)가 동시 접속한 결과, 시스템이 사실상 마비되는 현상을 관측했습니다.

* **지연 시간 급증**: `p(95)` 지표가 **11.68초**까지 치솟으며 목표치(500ms)를 23배 초과.
* **장애 발생**: 전체 요청의 **2.75%가 실패**했으며, 서버 응답이 없어 클라이언트 사이드 타임아웃 발생.
* **에러 원인 분석**:
   * **Status: 0**: 서버의 TCP Accept Queue가 포화되어 새로운 연결(SYN)을 수락하지 못함.
   * **HikariCP 고갈**: 모든 스레드가 DB I/O를 기다리며 차단(Blocking)되어 커넥션 풀이 즉시 소진됨.

---

## 3. 💡 해결 방식: 2단계 캐싱 아키텍처 적용

서버 리소스를 점유하는 DB 조회를 최소화하기 위해 캐시 레이어를 도입했습니다.

### 전략 1. Local Cache (v2)
* **방식**: `Caffeine Cache`를 사용하여 JVM 힙 메모리에 검색 결과 저장.
* **결과**: 네트워크 오버헤드가 없어 가장 빠른 응답 속도를 기록.
* **한계**: 서버 확장 시 인스턴스 간 데이터 불일치 위험 존재.

### 전략 2. Global Cache (v3) - **최종 채택**
* **방식**: `Redis` 서버를 구축하여 모든 서버가 공통 캐시를 바라보도록 구성.
* **결정 이유**: Local Cache보다 미세하게 느리지만(네트워크 비용), **데이터 정합성**과 **확장성**을 위해 분산 환경에 최적화된 Redis를 최종 아키텍처로 선정.

---

## 4. ✅ 결과 분석: 성능 비교 데이터

150 VUs 동일 조건에서 테스트한 결과, 모든 지표에서 압도적인 개선을 확인했습니다.

| 지표 항목 | v1 (Before) | v2 (Local) | v3 (Redis/After) | 개선율 (v1 vs v3) |
| :--- | :--- | :--- | :--- | :--- |
| **p(95) 지연 시간** | **11.68 s** | **94.02 ms** | **112.14 ms** | **약 104배 향상** |
| **에러율 (Fail Rate)** | 2.75% | **0.00%** | **0.00%** | **장애 0% 달성** |
| **초당 처리량 (TPS)** | 16.27 req/s | 72.46 req/s | **75.96 req/s** | **약 4.6배 증가** |
| **성공 요청 수** | 5,439건 | 26,390건 | **26,331건** | 가용량 대폭 상승 |

## 5. 📊 기술적 인사이트

* **지표의 중요성**: 평균값에 가려진 소외된 유저의 고통(`p(95)=11s`)을 확인하며, 성능 최적화의 기준을 상위 지연 시간에 두어야 함을 체감했습니다.
* **시스템 가용성**: `Status: 0` 에러를 통해 단순 소프트웨어 버그가 아닌, 인프라 리소스(Connection Pool) 임계점 돌파에 따른 시스템 붕괴 과정을 학습했습니다.
* **설계적 트레이드오프**: 가장 빠른 Local Cache 대신, 시스템의 정합성과 확장성을 위해 네트워크 오버헤드를 감수한 Redis 선택은 지속 가능한 성장을 위한 필수적인 결정이었습니다.
