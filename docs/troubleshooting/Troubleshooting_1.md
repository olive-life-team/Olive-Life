
# 🚨 Troubleshooting: 검색 API 성능 장애 개선 및 캐싱 전략 도입

검색 API 부하 테스트 중 발생한 **시스템 마비 현상(Request Timeout)**을 분석하고, **Redis 기반 분산 캐시**를 도입하여 성능을 100배 이상 개선한 과정

---

### 🔎 배경
* **기능**: 이커머스 서비스의 핵심인 상품 검색 API 구현
* **중요성**: 대규모 할인 행사나 광고 시점에 트래픽이 집중되므로, 동시 접속 상황에서의 안정성이 필수적임
* **기존 구조**: 별도의 캐시 레이어 없이 모든 검색 요청이 DB(`v1`)를 직접 조회하는 구조

---

### ⚠️ 문제 상황

150명의 가상 유저(VU)가 동시 접속하여 랜덤 키워드로 검색을 수행하는 시나리오에서 시스템이 완전히 붕괴되는 현상을 관측했습니다.

* **응답 지연**: `p(95)` 지표가 **11.68초**까지 치솟으며 사실상 서비스 이용 불가 상태
* **장애 발생**: 전체 요청의 **2.75%가 실패**했으며, 다수의 유저에게서 연결 끊김 발생
* **에러 로그**: 서버가 응답을 주지 못해 클라이언트 사이드에서 타임아웃 발생

#### 문제 재현 로그 (v1 부하 테스트 결과)
```text
ERRO[0339] GoError: the body is null so we can't transform it to JSON
http_req_duration..............: p(95)=11.68s
http_req_failed................: 2.75% (150 out of 5439)

// 상세 수집 로그 (Status: 0은 서버 응답 불능을 의미)
2026-04-19 07:23:14 - [v1] VU:124 | Status:0 | Msg:Error: request timeout
2026-04-19 07:23:14 - [v1] VU:150 | Status:0 | Msg:Error: request timeout
```

---

### ⚠️ 원인 분석

1. **DB I/O 병목 및 커넥션 풀 고갈**
    - 캐시 없는 직접 조회가 DB 디스크 I/O에 부하를 주었고, HikariCP 커넥션 풀이 즉시 소진되어 새로운 요청이 차단됨.
2. **스레드 차단(Blocking) 및 대기열 포화**
    - 모든 서블릿 스레드가 DB 응답을 기다리며 차단(Blocking) 상태가 되어 서버의 처리 능력이 마비됨.
3. **Status 0 (Request Timeout) 발생 원인**
    - 서버의 TCP Accept Queue가 꽉 차서 새로운 연결 요청(SYN)을 수락하지 못해 클라이언트에서 연결 실패 발생.

---

### 💡 해결 방식

서버 리소스를 점유하는 DB 조회를 최소화하기 위해 **2단계 캐싱 아키텍처**를 검토 후 적용했습니다.

#### 1. Local Cache (v2) 적용
* **방식**: 애플리케이션 메모리 내에 검색 결과를 보관.
* **장점**: 네트워크 통신이 없어 가장 빠름.
* **단점**: 서버가 여러 대일 경우 서버 간 데이터 불일치 가능성 존재.

#### 2. Global Cache (v3/Redis) 적용 (최종 선택)
* **방식**: 별도의 Redis 서버를 구축하여 전역 캐시 저장소로 활용.
* **이유**: 분산 환경에서 모든 서버가 동일한 데이터를 바라보도록 하여 **데이터 정합성**을 보장함.

#### 핵심 개선 포인트
- **DB 의존성 제거**: 자주 검색되는 상위 키워드에 대해 캐시를 우선 적용하여 DB 부하를 약 90% 경감.
- **분산 환경 고려**: 인스턴스 확장을 대비하여 Redis 기반의 글로벌 캐시 구조로 최종 확정.

### ✅ 결과: 성능 비교 데이터

150 VUs 동일 조건 부하 테스트 결과, 모든 지표에서 압도적인 개선을 확인했습니다.

| 지표 항목 | v1 (Before) | v3 (After/Redis) | 개선율 |
| :--- | :--- | :--- | :--- |
| **p(95) 지연 시간** | **11.68 s** | **112.14 ms** | **약 104배 향상** |
| **에러율 (Fail Rate)** | 2.75% | **0.00%** | **장애 0% 달성** |
| **초당 처리량 (TPS)** | 16.27 req/s | **75.96 req/s** | **약 4.6배 증가** |

---

### 📚 학습한 점

* **지표의 중요성**: 평균값에 가려진 소외된 유저의 고통을 보여주는 `p(95)` 지표의 중요성을 체감함.
* **시스템 임계점 이해**: 단순히 성능을 높이는 것을 넘어, `Status: 0`과 같은 지표를 통해 시스템이 무너지는 'Breaking Point'를 파악하는 법을 학습함.
* **설계적 트레이드오프**: 가장 빠른 Local Cache 대신, 정합성과 확장성을 위해 Redis를 선택하는 의사결정 과정을 경험함.

---

### ✍️ 한 줄 정리
